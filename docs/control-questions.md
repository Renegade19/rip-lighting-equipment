# Контрольные вопросы — Лабораторная работа №1

## 1. MVT (Model-View-Template)

MVT — вариант архитектурного паттерна MVC, часто используемый в связке
серверных фреймворков с шаблонизаторами (Django, а также любой backend
с server-side rendering, включая наш Go + gin + `html/template`):

- **Model** — представление данных предметной области. В проекте: структура
  `LightingEquipment` (`internal/app/ds/lighting_equipment.go`) и коллекция
  данных в `Repository` (`internal/app/repository`).
- **View** — обработчик, который выбирает данные и решает, какую страницу
  отдать (`internal/app/handler/lighting_equipment.go`).
- **Template** — HTML-шаблон с плейсхолдерами, в который подставляются
  данные модели (`templates/*.html`). Шаблоны обрабатывает стандартный пакет
  `html/template`, подключённый в `internal/api/server.go`
  (`r.LoadHTMLGlob("templates/*")`).

Отличие от классического MVC в названиях ролей: то, что в MVC называют
Controller, в MVT называется View, а то, что в MVC называют View, — Template.

## 2. Компоненты MVC в лабораторной работе

- **Model** — структура `LightingEquipment` и `Repository` (хранение и
  выборка данных: `GetPublishedLightingEquipment`,
  `GetLightingEquipmentForFeed`, `GetDraftLightingEquipment`).
- **View** — шаблоны `lighting-equipment-feed.html`,
  `lighting-equipment-draft.html`, `lighting-equipment-tile.html` и общая
  панель вкладок `lighting-equipment-tabbar.html`.
- **Controller** — `Handler` с тремя методами-обработчиками GET-запросов:
  они принимают HTTP-запрос, обращаются к Model (Repository) и передают
  данные в `ctx.HTML(...)` для рендеринга View.

Поток запроса: браузер → `Handler` (разбор URL и query) → `Repository`
(фильтрация, поиск, next) → `Handler` собирает данные для страницы →
`html/template` рендерит шаблон → HTML отдаётся клиенту.

## 3. Шаблонизация

Шаблонизация — подход, при котором HTML-страница собирается не вручную
конкатенацией строк, а через шаблон с плейсхолдерами и директивами
(`{{.EquipmentName}}`, `{{if}}`, `{{range}}`, `{{template}}`), которые на
сервере заполняются реальными данными перед отправкой клиенту.

Примеры в проекте:
- `{{range .LightingEquipment}}...{{else}}...{{end}}` в
  `lighting-equipment-tile.html` — рендер списка карточек, ветка `else`
  срабатывает на пустом списке.
- `{{if .Equipment.VideoURL}}...{{else}}...{{end}}` в
  `lighting-equipment-feed.html` — условный выбор video/img.
- `{{template "lighting-equipment-tabbar" .}}` — переиспользуемый блок
  (нижняя панель вкладок), подключаемый на всех трёх страницах.

Преимущества: разделение разметки и логики, переиспользование блоков,
более короткий и поддерживаемый код на сервере. Пакет `html/template`
экранирует данные с учётом контекста (текст, атрибут, URL), что защищает
от XSS.

## 4. HTTP и модель OSI

HTTP (HyperText Transfer Protocol) — прикладной протокол передачи
гипертекстовых данных, работающий поверх TCP (обычно порт 80/443).
В модели OSI (7 уровней) HTTP соответствует **7-му, прикладному уровню**
(Application Layer). Ниже него стоят:
- Transport (TCP) — надёжная доставка байтового потока;
- Network (IP) — маршрутизация пакетов;
- Data Link / Physical — передача кадров/сигналов по физической среде.

Каждый GET-запрос в нашем приложении (например `GET /lighting-equipment`) — это
HTTP-запрос: строка запроса (метод + URL + версия), заголовки (`Host`,
`Accept`, ...) и (для GET) пустое тело. Ответ сервера содержит статус-строку
(`200 OK` / `404 Not Found`), заголовки (`Content-Type: text/html`) и тело —
отрендеренный HTML.

## 5. Web

Web (Всемирная паутина) — система взаимосвязанных гипертекстовых документов,
доступных через интернет по протоколу HTTP(S), идентифицируемых через URI/URL
и отображаемых браузером. Основные составляющие Web: HTTP (протокол
передачи), HTML (язык разметки документов), URL/URI (адресация ресурсов),
браузер (клиент, интерпретирующий HTML/CSS/JS).

## 6. HTML

HTML (HyperText Markup Language) — язык разметки для описания структуры
веб-страниц с помощью тегов (элементов). Каждый элемент образует узел
DOM-дерева, которое браузер строит и отображает. В проекте HTML не пишется
руками для каждой страницы — он генерируется на сервере пакетом
`html/template` из файлов `templates/*.html` на основе данных модели
(см. пункт 3).

# Контрольные вопросы — Лабораторная работа №2

## 1. Виды баз данных

- **Реляционные** (PostgreSQL, MySQL, Oracle) — данные в таблицах со строгой схемой,
  связи через внешние ключи, язык запросов SQL, транзакции с гарантиями ACID.
  В проекте используется PostgreSQL.
- **Документо-ориентированные** (MongoDB) — записи-документы JSON без общей схемы.
- **Ключ-значение** (Redis, etcd) — быстрый доступ по ключу, обычно в памяти.
- **Колоночные** (ClickHouse, Cassandra) — хранение по столбцам, аналитика над
  большими объёмами.
- **Графовые** (Neo4j) — узлы и рёбра, запросы по связям.

## 2. SQL-запросы

SQL делится на группы:
- **DDL** — описание структуры: `CREATE TABLE`, `ALTER TABLE`, `DROP`.
- **DML** — работа с данными: `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
- **DCL** — права: `GRANT`, `REVOKE`.
- **TCL** — транзакции: `BEGIN`, `COMMIT`, `ROLLBACK`.

В проекте логическое удаление сделано сырым DML-запросом, без ORM:

```sql
UPDATE lighting_equipment
   SET equipment_status = 'удалён'
 WHERE CURRENT OF lighting_equipment_cursor;
```

Количество лайков считается подзапросом `COUNT(*)` к таблице связи,
а не перебором срезов в коде.

## 3. Курсоры

**Курсор** — указатель на результирующий набор запроса, позволяющий читать строки
по одной, не загружая весь результат в память. В PostgreSQL объявляется через
`DECLARE ... CURSOR FOR` и читается `FETCH`. Нужен, когда выборка большая либо
когда обработка строки зависит от предыдущей. Курсор живёт внутри транзакции.

В проекте курсор используется при логическом удалении
(`Repository.DeleteLightingEquipment`):

1. `BEGIN` — транзакция через `database/sql`.
2. `DECLARE lighting_equipment_cursor CURSOR FOR SELECT ... FOR UPDATE` —
   курсор по строке светильника, строка блокируется от параллельных изменений.
3. `FETCH NEXT FROM lighting_equipment_cursor` — чтение строки.
4. `UPDATE ... WHERE CURRENT OF lighting_equipment_cursor` — изменение именно
   той строки, на которой стоит курсор.
5. `CLOSE` и `COMMIT`.

## 4. ORM

**ORM** (Object-Relational Mapping) отображает таблицы БД на типы языка,
а строки — на объекты. В проекте используется **gORM**: таблицы описаны
структурами с тегами `gorm:"..."` (столбец, тип, ключи, ограничения),
а запросы строятся цепочкой методов `Where`, `Order`, `Take`, `Find`, `Create`, `Save`.

**Плюсы:** типобезопасность, отсутствие ручной сборки SQL, защита от SQL-инъекций
за счёт параметров, единое описание схемы.
**Минусы:** скрытая стоимость запросов (проблема N+1), сложные запросы всё равно
приходится писать на SQL, дополнительный слой абстракции.

Поэтому в лабораторной сознательно смешаны оба подхода: чтение, создание и
публикация — через ORM, логическое удаление — сырым SQL.

## 5. Модель и миграции

**Модель** — описание таблицы в коде: `LightingEquipment`, `LightingUser`,
`LightingEquipmentLike` в папке `internal/app/ds`.

**Миграция** — управляемое изменение схемы БД. При старте приложения таблицы
не меняются. Схема создаётся отдельной командой `go run ./cmd/migrate`
(`cmd/migrate/main.go`): создаётся тип-перечисление статусов и вызывается
`AutoMigrate` для трёх моделей. Это важно: изменение схемы при каждом запуске
на проде может незаметно сломать данные.

## 6. Чистая архитектура

Принцип: зависимости направлены внутрь, к бизнес-логике, а детали
(БД, фреймворк, шаблонизатор) находятся снаружи и заменяемы.

Слои в проекте:
- **Модели** (`internal/app/ds`) — предметная область, ни от чего не зависят.
- **Репозиторий** (`internal/app/repository`) — доступ к данным: фильтрация,
  переходы статусов, подсчёт лайков. Не знает про HTTP.
- **Обработчики** (`internal/app/handler`) — транспортный слой: разбирают
  параметры запроса и отдают данные в шаблон. Не знают про SQL.
- **Шаблоны** (`templates/`) — представление.

Благодаря этому замена шаблонов на React в следующих лабораторных
не затронет репозиторий, а смена способа доступа к данным не затронет обработчики.

# Контрольные вопросы — Лабораторная работа №3

## 1. Веб-сервис

**Веб-сервис** — программа, которая предоставляет свои функции другим программам
по сети через HTTP. В отличие от сайта, он отдаёт не готовые страницы, а данные
в машинном формате (JSON, XML). Клиентом может быть что угодно: SPA в браузере,
мобильное приложение, другой сервис.

В лабораторной бэкенд из ЛР2 превращён в веб-сервис: вместо шаблонов
`html/template` обработчики вызывают `ctx.JSON(...)`. Набор адресов и форматов
запросов и ответов называется **API** — он описан в `README.md`.

## 2. REST

**REST** (Representational State Transfer) — архитектурный стиль веб-сервисов.
Основные принципы:

- **Ресурсы и адреса.** Каждая сущность — ресурс со своим URL:
  `/api/lighting-equipment` — коллекция светильников, `/api/lighting-equipment/3` — один светильник.
- **Действие задаёт метод HTTP**, а не слово в адресе: `GET` читает, `POST` создаёт,
  `PUT` изменяет, `DELETE` удаляет.
- **Отсутствие состояния** (stateless). Сервер не помнит предыдущие запросы:
  всё нужное приходит в самом запросе.
- **Единообразный интерфейс.** Результат сообщается кодом ответа: `200`, `201`, `204`,
  `400`, `403`, `404`, `409`.
- **Представление.** Клиент получает не саму запись БД, а её представление — JSON,
  который собирает сериализатор.

В проекте: `GET /api/lighting-equipment` — список, `POST /api/lighting-equipment` —
создание (`201` и заголовок `Location`), `DELETE /api/lighting-equipment/7` — удаление (`204`).

## 3. RPC

**RPC** (Remote Procedure Call) — удалённый вызов процедуры: клиент вызывает
функцию сервера так, будто она локальная. В адресе или теле указывается
не ресурс, а действие: `POST /publishLightingEquipment`. Примеры: gRPC, JSON-RPC, SOAP.

Отличия от REST:

| | REST | RPC |
|---|---|---|
| В центре | ресурс (существительное) | действие (глагол) |
| Методы HTTP | несут смысл: GET, POST, PUT, DELETE | обычно один POST |
| Результат | код ответа HTTP | поле в теле ответа |
| Кэширование | работает для GET | обычно нет |

gRPC передаёт данные в двоичном формате Protocol Buffers поверх HTTP/2, поэтому
быстрее REST и удобен для общения сервисов между собой. REST проще и понятнее
для браузерных клиентов.

## 4. Заголовки и методы HTTP

**Методы:**

| Метод | Назначение | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | получить ресурс | да | да |
| POST | создать ресурс, выполнить действие | нет | нет |
| PUT | заменить или изменить ресурс | нет | да |
| PATCH | изменить часть ресурса | нет | нет |
| DELETE | удалить ресурс | нет | да |
| HEAD | как GET, но без тела | да | да |
| OPTIONS | узнать допустимые методы (используется в CORS) | да | да |

Безопасный метод не меняет данные. Идемпотентный при повторе даёт то же
состояние сервера, что и при одном вызове.

**Заголовки** — пары «имя: значение» со служебной информацией:

- `Content-Type` — формат тела: `application/json`, `multipart/form-data`.
- `Content-Length` — размер тела в байтах.
- `Accept` — какой формат ответа ждёт клиент.
- `Authorization` — данные для авторизации, например `Bearer <JWT>`.
- `Cookie` и `Set-Cookie` — куки от клиента и от сервера.
- `Location` — адрес созданного ресурса (ответ `201`) или адрес перенаправления.
- `Host`, `User-Agent`, `Cache-Control` — сервер назначения, клиент, правила кэширования.

**Коды ответа:** 1xx — информационные, 2xx — успех, 3xx — перенаправление,
4xx — ошибка клиента, 5xx — ошибка сервера.

## 5. Версии HTTP

- **HTTP/1.0** — на каждый запрос отдельное TCP-соединение.
- **HTTP/1.1** — постоянные соединения (keep-alive), заголовок `Host`, передача
  по частям (chunked). Запросы в одном соединении выполняются по очереди.
- **HTTP/2** — двоичный протокол, мультиплексирование (много запросов параллельно
  в одном соединении), сжатие заголовков HPACK. Работает поверх TCP.
- **HTTP/3** — работает поверх QUIC (на базе UDP). Потеря пакета не задерживает
  остальные потоки, соединение устанавливается быстрее, шифрование встроено.

## 6. HTTPS

**HTTPS** — это HTTP поверх TLS, порт 443. TLS даёт три вещи:

- **шифрование** — посторонний не прочитает данные;
- **целостность** — данные нельзя незаметно изменить в пути;
- **подлинность** — сертификат подтверждает, что сервер тот, за кого себя выдаёт.

Установка соединения (TLS handshake): клиент и сервер согласуют версию и набор
шифров, сервер присылает сертификат, клиент проверяет его по цепочке
удостоверяющих центров. Затем стороны с помощью асимметричной криптографии
получают общий сеансовый ключ, и дальше данные шифруются быстрым симметричным шифром.

## 7. Модель OSI (ISO)

Эталонная модель сетевого взаимодействия из семи уровней:

| № | Уровень | Что делает | Примеры |
|---|---|---|---|
| 7 | Прикладной | протоколы приложений | HTTP, DNS, SMTP |
| 6 | Представления | кодирование, шифрование, сжатие | TLS, JSON, UTF-8 |
| 5 | Сеансовый | управление сеансом связи | сеансы TLS, RPC |
| 4 | Транспортный | доставка между процессами, порты | TCP, UDP |
| 3 | Сетевой | адресация и маршрутизация | IP |
| 2 | Канальный | передача кадров в одной сети | Ethernet, Wi-Fi |
| 1 | Физический | передача битов по среде | кабель, радио |

Запрос Postman к веб-сервису проходит уровни сверху вниз: HTTP-запрос (7) →
сегмент TCP на порт 3000 (4) → пакет IP (3) → кадр (2) → сигнал (1).
На сервере — в обратном порядке.
